# Lumen Bot Investigation: Why Generated Bots Don't Match User Requests

## Executive Summary

**The user's question was:** "Why doesn't the bot do exactly what the user says? Is it model weakness or something else? Identify the weak points."

**Answer:** It was **NOT model weakness** (primarily). It was a **critical pipeline bug** in the LangGraph state reducer that silently discarded the user's request text before it ever reached the LLM. The architect agent received an empty string instead of the user's Arabic request, causing ALL spec backends to return `None`, which triggered the absolute fallback to a generic echo-bot template — regardless of what the user asked for.

**3 pipeline bugs were found and fixed.** After the fix, the generated bot now matches the user's request (e.g., the user asked for "تم الاستلام" reply → the generated handler replies "تم الاستلام"). There are also **5 model-level weak points** that remain, which stronger paid models would address.

---

## Root Cause #1 (CRITICAL — FIXED): User Request Text Lost in LangGraph Reducer

### The Bug

The `_merge_agent_state` reducer in `graph_builder.py` is the LangGraph channel reducer for the `agent` channel. LangGraph initializes every channel with its dataclass **default value** before the first node runs. For `AgentState`, that default is an **empty** instance:
- `user_text = ""` (empty string)
- `user_id = 0`
- `state_id = <random uuid>` (auto-generated by `default_factory`)

When `graph.invoke({"agent": real_state})` is called, the real state arrives as `right` while the empty default arrives as `left`. The old reducer **only kept `left`'s `user_text`** — it never copied `user_text`, `user_id`, `state_id`, `spec_request`, or `strict_spec` from `right`.

**Result:** The architect node received `user_text=''` → all three spec backends (`GeminiSpecBackend`, `BridgeSpecBackend`, `DeterministicSpecBackend`) checked `if not text: return None` → `produce_strict_spec` hit the absolute fallback → `spec_request="بوت"`, `purpose="fallback"`, `confidence=0.1` → generic echo-bot template.

### Evidence

**Checkpoint trace** (from `/tmp/lumen_output/langgraph_checkpoints.sqlite`):
- Thread `0a214534b8df476c` (the real state_id passed by the orchestrator):
  - Checkpoint #1: `state_id=370bf3c4d8054e2b` (WRONG — random UUID from empty default), `user_id=0`, `user_text=''`, `status=PENDING`
  - Checkpoint #2: Same wrong state_id, `spec_request='بوت'`, `strict_spec.purpose=fallback`, `last_node=plan`

**Unit test reproduction:**
```
TEST 2: left=EMPTY state (LangGraph channel default), right=state with user_text
  result.user_text = ''  ← BUG: should be the Arabic text
  result.user_id   = 0   ← BUG: should be 7631249810
  result.state_id  = stale_id_999  ← BUG: should be the real state_id
```

**Real LangGraph reproduction** (fresh thread, no checkpoint):
```
REDUCER: left_text='' right_text='REAL ARABIC REQUEST بوت تيليجرام' left_id=4781c40683ed47c4 right_id=fresh_test_001
REDUCER RESULT: user_text='' state_id=4781c40683ed47c4  ← user_text LOST
NODE_A: agent.user_text = ''  ← architect receives empty
```

### The Fix

The reducer now preserves identity-critical fields from `right` when `right` carries meaningful values:

```python
# Detect whether left is the empty channel default
left_is_default = (not left.user_text and not left.spec_request 
                   and not left.strict_spec and left.user_id == 0)
if left_is_default and right.state_id:
    left.state_id = right.state_id  # adopt real state_id on first merge
if right.user_text:
    left.user_text = right.user_text
if right.user_id:
    left.user_id = right.user_id
if right.spec_request:
    left.spec_request = right.spec_request
if right.strict_spec:
    left.strict_spec = dict(right.strict_spec)
# ... etc
```

### Verification After Fix

**Real LangGraph test:**
```
REDUCER: left_text='' right_text='REAL ARABIC REQUEST بوت تيليجرام'
REDUCER RESULT: user_text='REAL ARABIC REQUEST بوت تيليجرام' state_id=fresh_test_001  ← PRESERVED
NODE_A: agent.user_text = 'REAL ARABIC REQUEST بوت تيليجرام'  ← architect receives it
FINAL: user_text='REAL ARABIC REQUEST بوت تيليجرام'  ← end-to-end preserved
```

**Full pipeline test (real API keys, serial mode):**
- Architect received: `user_text='بوت تيليجرام بسيط: عند /start ترد أهلاً بك، وعند أي رسالة أخرى ترد تم الاستلام'`
- Spec: `source=gemini_architect`, `confidence=1.0` (NOT fallback!)
- Generated `app/handlers.py`: `message_handler` replies `"تم الاستلام"` — **EXACTLY matching the user's request**
- **Before fix:** generated generic echo bot saying `"لقد أرسلت: {text}"`
- **After fix:** generated bot matches user request

## Root Cause #2 (FIXED): InvalidUpdateError in Parallel Send Mode

### The Bug

`GraphState` scalar fields (`last_node`, `wave`, `done`, `isolate`, `hitl_decision`) had no reducers (plain `last_value` channels). When parallel `Send` workers ran simultaneously (multiple tasks in the same wave), each returned `{"last_node": "work", ...}`, causing:
```
InvalidUpdateError: At key 'last_node': Can receive only one value per step.
```

This crashed the pipeline whenever `MULTI_AGENT_PARALLEL=1` and the plan had 2+ parallel tasks.

### The Fix

Added `_last_write_wins` reducer for scalar fields and `_merge_task_ids` for `active_task_ids`:
```python
class GraphState(TypedDict, total=False):
    last_node: Annotated[str, _last_write_wins]
    active_task_ids: Annotated[list[str], _merge_task_ids]
    wave: Annotated[int, _last_write_wins]
    done: Annotated[bool, _last_write_wins]
    hitl_decision: Annotated[str, _last_write_wins]
    isolate: Annotated[bool, _last_write_wins]
```

## Root Cause #3 (FIXED): BridgeSpecBackend TypeError

### The Bug

`engine_groq_bridge.py` called `features_from_text(text, include_core=False)` but `features_from_text()` doesn't accept the `include_core` parameter (it's a stub returning `[]`). This caused a `TypeError` every time the Bridge spec backend ran, making it always fail and fall through to the deterministic backend.

### The Fix

Removed the unsupported `include_core=False` kwarg.

## Remaining Weak Points (Model-Level — NOT Pipeline Bugs)

These are **model capability issues** that stronger paid models would address:

### Weak Point #4: Gemini Flash-Lite Returns Empty Text for Architect Spec

**Evidence:** `Gemini parse failed source=GEMINI_API_KEYS[0] model=gemini-3.1-flash-lite schema=True: Gemini response has empty text`

The architect's first Gemini call (structured JSON spec generation) returned empty text. The pipeline retried with a different key and eventually succeeded, but this wastes time and keys.

**Recommendation:** Use `gemini-2.5-pro` or `gemini-2.5-flash` (not lite) for the architect/planner task. The per-task model override is already supported via `CLINE_MODEL_PLAN` env var — just set it.

### Weak Point #5: LLM Generates Syntax Errors

**Evidence:** Generated `app/handlers.py` had a duplicate line:
```python
async def message_handler(update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
    if update.message:
        await update.message.reply_text("تم الاستلام")   if update.message:  # ← DUPLICATE LINE (syntax error)
        await update.message.reply_text(update.message.text or "")
```

The `gemini-3.1-flash-lite` model produced malformed Python (overlapping/duplicate lines). A stronger model (Pro tier) would produce cleaner code.

**Recommendation:** Upgrade to `gemini-2.5-pro` for the build/worker task (`CLINE_MODEL_BUILD` env var).

### Weak Point #6: Planner Over-Decomposes Simple Requests

**Evidence:** For a simple "bot that replies welcome on /start and received on any message", the planner created 6 tasks including `feat_telegram_bot_api` (expected `modules/telegram_bot_api.py`), `feat_command_handling`, `feat_message_echo`, etc. The LLM generated `app/handlers.py` instead of `modules/telegram_bot_api.py`, causing `build_errors: ['merge_incomplete:modules/telegram_bot_api.py']` and `status=FAILED`.

The planner creates too many tasks for simple requests, and the file paths in the plan don't match what the LLM naturally generates.

**Recommendation:** (a) Use a stronger model for planning that better judges complexity. (b) Add a "simple bot" fast-path that skips multi-task decomposition for requests with <3 features.

### Weak Point #7: No maxOutputTokens Set for Gemini

**Evidence:** `gemini_client.py` generation config has `temperature` and `responseSchema` but **no `maxOutputTokens`**. The model uses its default output limit, which may truncate longer code generation.

**Recommendation:** Add `"maxOutputTokens": 8192` (or higher) to the `generationConfig` in `gemini_client.py`.

### Weak Point #8: All Models Are Flash-Lite (Weakest Tier)

**Evidence:** `_MODEL_FALLBACKS` in `gemini_client.py`:
```python
_MODEL_FALLBACKS = (
    "gemini-3.1-flash-lite",
    "gemini-3-flash-preview",
    "gemini-3.5-flash-lite",
    "gemini-flash-lite-latest",
    "gemini-flash-latest",
)
```

All are "flash-lite" (the cheapest/weakest tier). None are "pro" or even regular "flash". The comment notes these were chosen for "live availability" (19/30 keys working for flash-lite vs 14/30 for others), but this trades quality for availability.

**Recommendation:** Add pro-tier models to the fallback list for the architect and build tasks. Even if fewer keys work, the quality improvement is worth it. Set `GEMINI_MODEL=gemini-2.5-pro` or use `CLINE_MODEL_PLAN` and `CLINE_MODEL_BUILD` env vars.

## Conclusion

**The primary reason generated bots didn't match user requests was a pipeline bug (Root Cause #1), NOT model weakness.** The user's request text was silently discarded by the LangGraph state reducer before it ever reached the LLM. This has been fixed and verified.

**After the fix**, the generated bot now matches the user's request (the "تم الاستلام" handler is direct evidence). However, **quality can be further improved** by upgrading to stronger paid models (Pro tier instead of Flash-Lite) for the architect and build tasks, setting `maxOutputTokens`, and adding a simple-bot fast-path to avoid over-decomposition.
